# 截图建议核查与照片识别续修

核查日期：2026-11-05（北京时间）。用户要求继续修复，并验证三张建议截图是否可靠。截图与用户业务照片均未上传仓库；本文只有通用规则、公开文档链接及虚构反例。结论是部分工程方向合理，但截图没有提供能证明字段准确率或报警准确率提升的对照数据，不能把格式正确或复识一致当成识别正确。

## 逐条核查

| 截图建议 | 核查结论 | 适用边界 |
| --- | --- | --- |
| 强制 JSON Schema | 有助于机器解析和字段类型约束，不能保证读出的值与原图相同 | 在提示词中写“纯 JSON”与调用 API 的受约束输出不是同一回事；仍须校验内容。Google 官方明确要求处理结构合规但语义错误的输出。 |
| 正则约束编号与时间 | 可拒绝部分格式错误，不能检测所有误读 | 截图的 `JL1KF\d+` 只接受数字后缀。虚构 `JL1KF12A34` 完整匹配失败，若用子串搜索只匹配到 `JL1KF12`；不能把子串匹配当整串校验。两个不同但合法的时间也都会通过格式校验。 |
| 白名单与编辑距离自动纠错 | 白名单可用于提示和校验，直接按最近项覆盖不可靠 | 白名单须经核实且覆盖实际范围；多个候选等距时不能自动选择，即使唯一最近也不证明原图就是它。保存原读数，未知、歧义项保留核对。 |
| 少样本示例 | 合理的提示设计方法，实际收益须测量 | 使用正确标注、版式有代表性的示例；保留独立验收图片。Google 指出过多示例可能导致过拟合。结果页中的疑似误识不能直接作为真值。 |
| 温度统一设为 0 或 0.1 | 不是通用可靠配置，更不保证识别准确 | Google 当前文档说明低温也不是完全确定；部分新模型忽略自定义采样参数，较早 Gemini 3 模型建议保留默认设置。截图未给出具体模型/API，不能据此一概调低温度。 |
| 双引擎投票与不一致触发复核 | 不一致触发复核合理，双引擎“投票解决”表述过强 | 两份不同结果是 1:1，没有多数；一致也可能共同出错。此前实测是同一 Apple Vision 的不同设置，不能冒称已经验证了两个独立模型。 |
| 分块识别后聚合 | 可能有帮助，需验证行列关联与漏行 | 保留表头、原坐标及重叠，检查重复行和跨行串列；Google 文档说明较高媒体处理分辨率可帮助读取细小文字，代价是更多 token 与延迟，不能凭分辨率高就断定图像会识别更差。截图末尾被遮挡的内容不作完整归纳。 |

原提示词还有两处需要修改：一是“合理推断”不适合自动补齐关键编号、圈号或时间；二是五字段输出丢失完整日期、站名、应急及 test 状态，不能作为完整运维计划的内部记录。原图实际警告应与 OCR 自身疑项分别保存，字段无法辨认时应有明确的缺失/待核对表示。

6. 运行 `python3 scripts/verify_plan_claim_examples.py` 可复现完整正则与子串的区别、合法格式但错误时间、编辑距离并列、双票平局和一致但错误五类反例。脚本不调用模型，不是 OCR 准确率基准。

## 当前 App 与续修范围

当前 App 调用本机 Apple Vision，不调用 Gemini/LLM Vision，也没有在此识图流程中使用 Prompt 或 temperature。已有完整日期、行位置、原图裁条及核对流程。截图的部分建议可作为将来另建 LLM 提取入口的设计依据，但不能宣称改提示词已改变本机 OCR。

Build 522—524 的原格读数把虚构图中 `DEMO07D02` 读成 `DEM007D02`，多个设置共同读错。新的独立分支 `codex/plan-id-character-20261105` 保留名称片段、完整原格候选及前后缀约束；主读数仍用 accurate，仅在没有可支持候选时，用剩余的同一份每页 64 次预算试验 fast 字符识别路径。原有多个候选之间的歧义不交给下一种设置自动裁决。

此前另一组模糊六格中的 fast 曾为 0/6，所以这里不把它全局启用，也不预设会改善。本轮保留失败用例的图像与全部断言，要求真正读出完整正确编号，其余五行场景保持；另记录同一虚构像素的 2 倍/4 倍缩放读数，仅作诊断。四张冻结全图及真值不变，和 Build 521 的 188 条记录逐字段对照，分别报告错→对、对→错、仍错与无法独立对应的变化。
