# 值班提醒 产品与架构路线图

> 2026-10-13 第一版。依据：通读全部源码（约 2 万行），加上架构审查和真实使用流程审查。
> 每完成一项就在「状态」里打勾，并在文末「迭代记录」补一行。

## 一、现状诊断

### 产品短板（用户视角）
1. **同一个问题有多个答案**：「下次遥测」在今天页、遥测预测、排班预演、排班规律、小组件里各算各的（3 种算法），小组件只认已排好的日子，常和今天页对不上。
2. **今天页过载**：最多 16 个区块；还挂着 SideStore/LocalDevVPN 续签横幅，而现在主推 TestFlight。
3. **危险操作没有确认、没有撤销**：清除变动记录、还清换班账、恢复默认班次、清除全部手动修改、工作留痕左滑删除等约 15 处一点就没。
4. **同步失败不显眼**：24 小时后才出红色横幅，之前只是今天页底部一行灰字；横幅说「到设置›诊断」却点不过去；小组件不显示数据是否过期。
5. **换班不好用**：「找人换班」只列名单，不能直接发请求；换班账本只有管理员能用，但它本来是个人的「谁欠我班」。
6. **很多数据收集了却没用起来**：网站公告变了不提醒；排班预演、节假日预留名单、卫星信息、待休天数没进小组件、日历和提醒；日历页只显示自己的班。
7. **自动化要用户自己搭**：后台同步要用户手动建 4 条以上快捷指令自动化。
8. **术语太多**：自动判断、只按排班算的人、模型、猜中、规则版本……普通同事看不懂。
9. **班次没有起止时间**：「值班到明天 08:30」是写死的，没法做「上班前 1 小时提醒」、实时活动倒计时。
10. **无障碍、iPad、多语言基本没做**：固定字号 38 处，无障碍标签只有 3 个。

### 架构短板
1. **AppStore 是 2200 行的「上帝对象」**：同步、存储、通知、微信、备份、权限、演示数据全在一起；服务反过来依赖 `AppStore.shared`，无法单独测试。
2. **AppSettings 有 110 多个字段**，偏好、缓存、日志、去重标记、设备本地数据混在一起，每个字段都要手写解码。
3. **每改一个设置就整份重写 state.json 并重排通知**；一次同步要写 15–20 次；多文件写入不是原子的。
4. **权限靠 didSet 偷偷改回去**，界面上看到「改了又跳回」，没有任何提示。
5. **重计算在主线程**：`matcher` 每次访问都重建，`ShiftMatcher.match` 每次都重新整理关键词；轮转推算在 3 处各算一遍。
6. **缓存失效靠「人数/天数」判断**：换岗但人数不变时页面不刷新。
7. **拆分「+」的规则不一致**：有的地方只按「+」拆，匹配器还认「、,/」，导致已排班日子和图标判断可能不一致。
8. **大量策略逻辑在 App 里没有测试**：同步接受策略、提醒时间表、图标、微信去重、恢复迁移等。

## 二、重构方案（分步，每步都能单独上线、不破坏功能）
| 步骤 | 内容 | 状态 |
|---|---|---|
| R1 | 一个共享的 `ShiftMatcher`（只在班次类型变化时重建）、关键词预先整理；统一用 `ShiftMatcher.posts(_:)` 拆岗位 | ☑ |
| R2 | 存储去抖：设置变化只标「脏」，0.5 秒内合并成一次写盘；`roster.json` 读坏时另存备份 | ☑ |
| R3 | 同步过程先在副本上改设置，最后只赋值一次 | ☑ |
| R4 | 把纯策略搬进 ShiftCore 并补测试：同步接受策略、提醒时间表、图标、微信时间与去重、日报文字 | ☑ |
| R5 | `DerivedDataCache`：用真正的数据版本号做缓存键，轮转、待休预警、下次遥测、工作量在后台算好再发布 | ☑ |
| R6 | AppSettings 拆成：用户偏好 / 管理员规则 / 同步状态与缓存 / 通知去重 / 设备本地，一次性迁移并有测试 | ☑（分类整理，存档格式不变，见迭代记录） |
| R7 | AppStore 拆服务：RosterRepository、NotificationScheduler、SyncCoordinator（`SyncStatus` 枚举代替文字前缀判断）、WeChatNotifier、BackupService；AppStore 只做门面 | ☑（按职责拆成文件，见迭代记录） |
| R8 | 权限改成显式：管理员才能调用的修改走方法，非管理员给出提示，而不是悄悄改回 | ☑ |
