## 本轮确认并修复的问题

| 编号 | 触发条件与影响 | 修复范围 |
|---|---|---|
| A01 | 恢复文件只有 `settings`，或排班字段类型损坏时，旧入口把缺失/坏字段当成空字典，可能清空现有排班 | `BackupArchive` 在任何状态提交前校验版本、核心段、日期和重复日期；合法空备份与旧格式仍支持 |
| A02 | 工作留痕开关锁迁移时，两个目录已有同名索引或某个文件移动失败，旧代码忽略错误后删除整个源目录 | 改为整目录移动；非空目标保留两边并报错；保存、迁移成功后才改变锁设置；启动恢复失败禁止写空索引 |
| A03 | 工作留痕索引损坏，保留损坏文件的操作也失败，旧代码仍开始空索引，后续可能覆盖原件 | 恢复副本使用唯一文件名；保留副本失败则阻止写入，并显示可重试错误 |
| A04 | 本地身份认证能力检查失败，旧代码直接设置 `unlocked = true` | 无法验证时保持锁定；设备尚不能认证时拒绝启用锁，不把失败当验证成功 |
| A05 | 旧备忘数据同时含补零/未补零的同一天键，构造提醒字典时重复键触发崩溃；日期解析还会丢掉非法片段后误接收 | 备忘确定性归一化并优先正规键；`DayKey` 必须恰好三个非空数字部分，继续支持旧版未补零日期 |
| A06 | 外部计划导入后进入运营商设置再返回，`onAppear` 再次导入旧内容，重置已修改行和已发进度；自动扫描也会重复弹出 | 同一入口只消费一次，新入口和新扫描请求仍可接收 |
| A07 | 分享面板仅复制或存到相册，`completed = true` 也被记为已发，可能推进下一家并取消当天计划提醒 | 明确本机活动、取消、错误和无活动类型不记已发；每个面板至多完成一次；未知第三方扩展保持兼容 |
| A08 | 文件/照片统一删除卫星标识前的 1–4 位数字，如 `12AB34` 被改为 `AB34` | 删除无证据清洗，保留标识原串；照片仍须人工核对；保留已有几何行号隔离逻辑 |
| A09 | 公历日期交给佛历/日本历构造计划提醒，可能落在错误年份 | 统一公历，保留设备时区，并把公历写入通知日期组件；本次未改变重复提醒语义 |
| A10 | 同步在网络或通知等待期间切换使用者/来源或恢复备份，旧任务继续写回旧排班和成功状态 | 主数据及外层状态提交前重新校验同步输入与取消状态；有效恢复在提交前取消旧同步；等候者可以重新启动有效同步 |
| A11 | 按“值班提醒”名称认领已有日历，删除同日重复/无排班事件；关闭同步删除整本日历 | 新版独立管理标识，只处理精确所有权标记的事件；不按标题认领，不删除整本日历；旧事件保留 |
| A12 | 微信早/晚/周提醒在同步或 HTTP 前先持久标记已发，中断后会漏发；失败回滚可能覆盖另一请求已成功的标记 | 使用内存发送中状态共享防重；成功且有排班内容后才提交完成标记，失败不回滚其他请求 |
| A13 | 实时活动尚未创建成功就记下展示时间；创建失败后仍会被“已展示”规则抑制 8 小时 | 仅在 `Activity.request` 成功后记录展示日期和时间；本轮未注入真机 ActivityKit 失败 |

分享系统的完成回调不是收件人送达回执；本轮没有猜测微信或“存储到文件”等扩展的私有活动标识。因此，未知第三方扩展不能据此认定都属于聊天发送。

日历安全迁移有明确取舍：旧版没有所有权标记的日历和事件保留，首次升级可能出现新旧排班并存。关闭同步清理近期本版生成的排班，保留日历本身、窗口外历史和用户自行添加的事件。没有依据标题自动迁移或删除旧日历。

## 已确认、尚未修复或未验收的项目

1. **计划“每天提醒”和周会“每周一提醒”只登记下一次单条通知。** 两个请求均为 `repeats: false`，首次通知后若主 App 未再次获得执行机会，不会自行继续登记下一周期。需要统一考虑未来通知预算、当天已发抑制和重复规则，不能只把一个布尔值改成重复通知后声称完成。
2. **其他微信摘要和业务通知仍有状态窗口。** 本轮 A12 覆盖早/晚/周排班提醒，未扩展到月报、管理周报、个人周小结等全部摘要；它们仍有预写标记或失败处理差异。A10 的外层检查也不会撤销已进入通知 helper 的内部副作用：例如公告/全员变动等待本地通知后，仍可能用变更后的推送配置发送此前生成的内容。HTTP 成功和本地持久化之间的进程终止，也不能在没有服务端幂等支持时承诺严格仅一次送达。
3. **主屏 App 图标后台自动跨日仍未实现可靠保证。** 现有实现仅前台更新；后台唤醒不是定时保证。已有“今日班组”小组件预生成跨日内容，具体展示时刻由系统安排。
4. **密集图片 OCR 精度仍未合格。** Build 496 的历史原生结果、网页状态识别缺口与 Probe 7 的无收益结论仍保留。新标识保真修复不等于 OCR 更准；人工审核约束保留。用户真实照片未运行新的 Apple Vision 验收。
5. **真机边界未验证。** 本轮不能替代 iPhone 17 Pro Max 上的跨夜后台、Face ID、分享扩展、真实 EventKit 权限/同名日历与文件保护状态验证。
6. **AlarmKit 闹钟重排仍有中断窗口。** 当前先撤销旧闹钟，再用随机 ID 逐个创建新闹钟，最后保存整批 ID。中途失败可能使原提醒丢失；创建成功但 ID 未保存就结束进程，可能留下下次无法识别的闹钟。该路径已通过源码核实，未注入真机故障，尚未改造登记事务。
