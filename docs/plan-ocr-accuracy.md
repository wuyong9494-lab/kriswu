# 数传计划拍照识别修复交接

## 当前任务与基线

- 用户反馈：值班提醒 App「拍照识图发计划」仍大量认错。
- 范围是运营商数传计划的拍照识别、按地面站分家、核对与分享；现有实现为本机 Apple Vision 加表格几何解析。
- 从最新开发提交 `bbdbc34a953452b0e394fba423126139f53db994` 创建 `codex/plan-ocr-accuracy`，没有从旧 main 开始。实际照片规则在同一修复链的 `codex/plan-photo-rules` 验证，保留上一轮正在运行的 OCR 对照。
- 首次修复提交：`75087f9c00a34c5b86641256abfa0cda2c9db0b9`。
- 首轮验证：[iOS Build 486](https://github.com/wuyong9494-lab/kriswu/actions/runs/41571843067)。
- 页面拆分修复提交：`c3d7caf623ac9b314d0b44eea8c22a2c8a6979ba`。对照运行：[iOS Build 487](https://github.com/wuyong9494-lab/kriswu/actions/runs/41572618165)。
- 用户补充了四张实际拍屏照片：网页表格在序号列左侧用无表头的独立「应急」标签，最右侧为状态列；照片之间有重叠行、不同缩放和拍摄倾斜。
- 用户确认规则：左侧「应急」按应急计划处理；右侧状态为 `test` 的行不发给任何运营商，包含应急行。其他状态保持原有处理。

## 已落实的行为

1. 同时开始的计划通过卫星名称或 ID、圈次与结束时间核对，要求双向唯一关联；不再只按开始时间套用站名。
2. 时间必须完整匹配并满足真实公历日期；坏秒、尾随杂字和不存在的日期保留待核对。
3. 跨页仅合并身份唯一一致的条目；圈次不独立代表卫星身份，同页不按相同时间删行。
4. 多次 OCR 的合法值相互冲突时，保存 `recognitionIssues`。重排、合并和补全不能清除这些提示。
5. 地面站局部复识不覆盖已知站。未知站必须有两次一致且匹配明确运营商规则的读数；未知到未知不替换。
6. 重新拍到几何表头时更新后续无表头页的列位置；系统表格识别的整数列号不会作为照片坐标。
7. 运营商最长前缀归属不唯一时保持未分配。应急值不再根据任意“是”字开头判断。
8. 编辑页显示原照片表头和当前行，可横向查看。保存并确认只清除 OCR 分歧；无效时间、缺少字段等检查继续生效。
9. 分享前要求处理实际疑项。开启“发原图”而缺少切片时，明确说明缺图，不再悄悄改用 OCR 重绘图。
10. 图片缓存绑定完整输入和源批次；异步读取、编辑保存、分享回调都核对批次，防止旧结果覆盖新计划。

## 实际版式补充

- 独立关联左侧无表头应急标签和右侧状态，要求唯一行几何匹配，保留应急与 test 证据，不能由整行背景色推断。
- 全部发送出口共用 test 排除规则：按运营商分组、文字表格、重绘图片、原图裁条、日期标题、应急附言、依次分享和已发统计。
- 照片中有状态列、该行却未读到状态时记录待核对问题，不能直接当作可发送；对照原图保存确认后可解除该识别疑问。
- 保留被排除的原始条目，在页面「test · 不发送」区可对照照片核对，且不计入待发送家数。
- 编辑应急时同步独立标签与显式列；只有明确修改状态或对照原图确认状态不是 test，才清除之前读到 test 的证据。
- 模拟器回归仅使用匿名合成版式，不将用户实际照片或其中业务数据提交到公开仓库。
- 原图裁切先用全部行（包括 test）限定上下边界，再按发送规则过滤；几何交叉的行放弃不可靠原图并提示核对。
- 新增 20 项 `PassPlanDeliveryRulesTests`，涵盖版式、列位置、歧义、跨页证据、精确状态、表格重新导入和裁片边界。
- 新增两张匿名网页图片及实际 OCR 回归；另检查原图出口排除 test、缺少 test 裁片不影响正常行、仅有 test 时不输出图片，以及邻行测试色带的像素隔离。

## 验证设计

- 新增 `PassPlanRecognitionTests` 25 个测试方法，覆盖坏时间、日历日期、站名关联、反向唯一性、跨页去重、冲突保留、应急、旧 JSON 兼容与规则歧义。
- 两处旧测试调整了已证实不可靠的假设：名称错字去重需明确相同卫星 ID；应急未知提示不再声称按非应急发送。
- `PlanReaderTests` 真正运行四组既有合成照片；识别失败、空结果、没有可唯一对应真值的行会使测试失败。
- 准确率报告使用全部真值作分母，逐项记录站名、运营商、卫星、圈号、开始/结束时间、应急未知以及无法对应的行。未知应急不算正确的“否”。
- `[plan-ocr-tests]` 使用既有 SiteTests 目标，只运行 PlanReaderTests，并优先选择 iPhone 17 Pro Max；实际设备、日志与 xcresult 保存为 Actions artifact。
- 保留完整 App 编译和零并发警告门槛。原有 Metal completion handler 先取出 String? 错误消息再进入 MainActor，解除基线已有的 buffer 跨 actor 警告，不改变渲染行为。
- 本地 Swift 6.2 的语法解析及核心严格并发类型检查通过。完整 SwiftPM 在当前环境进程统计路径崩溃，不能将它当作通过证据。随后使用直接编译器构建实际 `PassPlan.swift` / `DayKey.swift` 模块和原有 XCTest 方法，独立执行原 27 项、新增识别 25 项、实际版式 20 项，共 72 项，全部通过。该结果覆盖计划核心逻辑，不能替代完整 App 或 Apple Vision 测试。

## 发布与剩余验收

- `codex/plan-` 修复分支均排除自动更新 Releases 最新侧载包，不自动上传 TestFlight。
- 已取得并逐张查看四张实际照片，找到了无表头应急标签被分配进序号列后丢失的原因。目前执行环境不能运行 Apple Vision；真实照片尚未实际跑过本机 iOS OCR。匿名合成版式不能替代实际拍照验收，不能声称真实照片准确率或真机问题已经全部解决。
- 真实 OCR 的最低执行契约不等于精度验收，必须阅读逐字段结果，并针对剩余误识补充样例。

### 密集图耗时定位

- 代码审查确认：拆格复识的 400 次计数在每次 `recognize` 内重新开始。4032×3024 样例会产生 7 段原图、7 段平滑图和一次整图识别，理论上限因此达到 6000 次拆格复识。这是代码上限推算，不能当作运行时实测次数或断言唯一耗时原因。
- 将拆格复识预算限定到每张照片，在识别前按既定顺序分配给各轮次和各段，避免并发完成顺序决定谁获得预算。预算不足以拆完整组时保留原始 OCR 框，不删除行，也不减少主要识别轮次。
- 增加三项预算回归：所有轮次和分段总额不超过 400、不能只复识半组、零预算和小预算不超支；站名独立确认与应急/状态窄栏识别仍保留。
- 测试启用阶段诊断，只输出阶段、图片尺寸、计数和耗时，不记录识别文字；用于区分主要文字识别、拆格复识、系统表格识别、站名与标记复识、裁条等环节。默认 App 识别不启用该诊断。
